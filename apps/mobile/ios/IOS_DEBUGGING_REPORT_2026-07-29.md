# iOS IPA 调试复盘报告（2026-07-29）

## 1. 结论摘要

本轮调试从已确认有效的 iOS 启动闪退修复 `8adf960` 之后开始，围绕以下问题进行了多轮诊断和试验：

- 远程导入角色卡后列表不能即时显示；
- 安装第三方扩展后需要重启或刷新；
- 角色详情面板显示默认值或空值；
- 世界书能够被选择，但条目列表或展开内容为空；
- 创建角色按钮无反应；
- 后期版本出现顶部按钮和右侧面板整体消失。

最终证据表明：

1. 在已观测样本中，角色卡和世界书持久化数据能够被完整读出，不能据此认定 IndexedDB 数据损坏。
2. IPA 运行时曾出现两套关键 Legacy UI DOM。业务逻辑写入其中一套，而用户看到的是另一套，因此表现为多个功能同时“没有数据”。
3. 第二套 UI 的来源没有被最终定位。它是在 `DOMContentLoaded` 之后异步出现的，但尚无证据证明具体由哪个脚本、路由或原生壳生命周期创建。
4. 后续加入的 DOM guard 属于基于现象的清理措施，不是根因修复；最新版 guard 误删了主 UI 容器，造成顶部按钮、角色面板和世界书界面消失。
5. 本轮多个提交混合了诊断、刷新兜底、DOM 修补和 Web 生产代码中的 iOS 专用逻辑，扩大了回归面，应全部撤销。

因此，`main` 回到 `8adf960` 的代码基线，仅保留本报告，不保留本轮调试和试验实现。

## 4. 已确认的日志证据

### 4.1 数据并非普遍丢失

诊断期间能够观察到：

- 导入的角色卡记录能够在重启后出现在列表；
- 角色对象及其嵌套 `data`、`json_data` 字段能够被读取；
- 角色描述、首条消息等字段在内存对象和部分表单节点中具有实际长度；
- 世界书存储记录能够读取到 24 个条目，样本条目结构完整。

这些证据只能说明已测试记录能够持久化和读取，不能证明所有数据层实现绝对正确；但它们足以否定“当前所有界面为空都是数据库没有写入”这一假设。

### 4.2 存在两套关键 UI

诊断日志曾显示下列关键节点同时出现两份：

- `#right-nav-panel`
- `#form_create`
- `#description_textarea`
- `#firstmessage_textarea`
- `#world_editor_select`
- `#world_popup_entries_list`
- `#world_info_pagination`

其中一套角色表单已经写入真实字段，但不可见；另一套处于用户可见/可操作状态，却仍是默认值或空值。这能够统一解释：

- 点击角色卡后面板没有角色内容；
- 创建角色按钮没有作用；
- 世界书下拉选择存在，但条目内容不显示；
- 重启后问题仍可复现。

### 4.3 重复 UI 在 DOMContentLoaded 之后出现

在失败版本中，`DOMContentLoaded` 时关键节点计数仍为 1。大约数秒后计数才变为 2。因此，`795a928` 在 `DOMContentLoaded` 后立即结束 observer 的策略无法处理真实时序。

这只能证明“第二套 UI 延迟出现”，尚未证明其创建源。不能把自定义 scheme handler、Legacy 路由、脚本重复执行或其他生命周期机制中的任何一个直接定为根因。

### 4.4 长期 DOM guard 导致明确回归

以下两份真机日志来自 `81d8dc0` 构建：

- `PureTavern-0.1.7-ios-unsigned.ipa_2026_7_29_1_50_30.log`
- `PureTavern-0.1.7-ios-unsigned.ipa_2026_7_29_1_51_1.log`

第一份日志中：

- `17:50:08`：`ios-dom-guard.pruned` 显示关键 UI 计数均为 1；
- `17:50:12`：observer 执行清理，报告移除 2 个 root；
- 清理后 `rightNavHolder`、`rightPanel`、`worldDrawer`、`worldEditor`、`worldEntries`、`worldPagination` 全部变为 0，仅 `chatRoot` 保持 1。

第二份日志在 `17:50:45` 再次出现相同结果：observer 清理后角色和世界书 UI 计数为 0。

这与真机观察到的“顶部按钮看不到、UI 显示整体异常”完全一致。结论是 guard 将承载有效界面的主容器一并删除，而不是安全地只删除重复副本。

## 5. 为什么多轮修改仍未解决

### 5.1 过早把问题归因于资源或数据即时可见性

最初症状是导入后需要重启才能看到，因此先后尝试了实时资源 Provider、列表刷新和页面重载。它们可能改变表面行为，但无法解释创建角色、角色详情和世界书同时异常。

### 5.2 用刷新掩盖生命周期问题

强制刷新可以让部分持久化数据重新进入初始化流程，但没有证明初始化过程中为什么存在两套 UI，也无法保证详情编辑和世界书渲染使用同一套节点。

### 5.3 在未定位创建源前清理 DOM

仅凭重复 ID 就删除其直接 body 容器风险很高。Legacy 页面结构并不保证每个重复节点都位于独立、可安全删除的文档根中；清理一个祖先可能同时删除有效顶部导航、右侧抽屉和世界书节点。

### 5.4 诊断和修复没有严格分离

诊断提交中逐渐加入了恢复、布局和刷新行为，使日志观察对象本身被改变。正确做法应是先加入只读、可移除的诊断，收集到创建调用栈或脚本来源后再单独提交修复。

### 5.5 缺少 Mac 端实时 WebKit 调试闭环

当前主要通过 Windows 修改、macOS CI 打包、真机安装、导出日志来验证。每轮反馈周期长，而且系统日志无法替代 Safari Web Inspector 中的 DOM 断点、网络请求 initiator、脚本调用栈和 WebView navigation 观察。

## 6. 当前根因状态

### 已确认

- `8adf960` 之前的启动闪退来自 Capacitor scheme handler 重复注册。
- 导入、详情、创建和世界书异常具有共同的 UI 生命周期特征。
- 运行时曾存在两套关键 Legacy UI。
- 第二套 UI 在 `DOMContentLoaded` 后异步出现。
- `81d8dc0` 的长期 DOM guard 会误删主 UI。

### 尚未确认

- 第二套 UI 是由哪一个脚本、路由、导航或原生 bridge 调用创建；
- 是否发生了完整脚本二次执行，还是仅发生局部模板二次挂载；
- 自定义 `WKURLSchemeHandler` 是否直接参与第二次文档创建；
- WebView 的页面缓存、恢复或 Service Worker 是否参与该时序；
- 角色导入即时不可见与重复 UI 是否完全同源。

在获取创建调用栈前，不应继续声称已经找到最终根因。

## 7. 后续调试建议

如果未来重新处理该问题，建议使用以下顺序：

1. **在 Mac 上使用 Xcode Debug 构建。** 不再依赖每次 CI 生成 IPA 才观察一个假设。
2. **连接 Safari Web Inspector。** 对 `#rightNavHolder`、`#right-nav-panel` 和 `#world_popup_entries_list` 设置 DOM subtree modification breakpoint，捕获第二次创建的 JavaScript 调用栈。
3. **记录 WebView navigation。** 在 `WKNavigationDelegate` 中记录 request URL、navigation type、main frame、redirect 和进程终止/恢复事件，确认是否发生第二次主文档加载。
4. **建立最小 Capacitor 对照。** 分别测试标准 Capacitor handler 与 PureTavern 自定义 wrapper，逐项启用资源桥，确定最小触发条件。
5. **保持诊断只读。** 诊断代码不得刷新页面、调用上游渲染函数、修改布局或删除 DOM。
6. **一次提交只验证一个假设。** 每个实验都应有明确预期、真机日志标识和可独立回撤边界。
7. **限制平台代码范围。** iOS 专用实现优先放在 `apps/mobile/ios/`；除非形成通用平台抽象并有跨平台测试，否则不修改 `apps/web/` 生产逻辑。
8. **先定义验收矩阵。** 至少覆盖：冷启动、热启动、导入角色卡、创建角色、打开详情、选择并展开世界书、安装扩展，以及应用重启后的持久化状态。
